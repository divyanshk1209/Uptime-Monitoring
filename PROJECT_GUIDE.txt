PULSEBOARD PROJECT GUIDE
========================

1. PROJECT SUMMARY
------------------

Project name: PulseBoard

PulseBoard is an end-to-end full-stack web application for monitoring website or API uptime.

In simple words:
You enter the name and URL of a service, such as https://example.com. The application stores that service in PostgreSQL. Then you can click "Run check" from the dashboard. The backend sends an HTTP request to that URL, checks whether the response status matches the expected status code, stores the result in the database, and shows the latest status on the frontend.

This project is good for a resume because it shows:

- Frontend development using React and TypeScript
- Backend API development using Python and FastAPI
- Database design using PostgreSQL and SQLAlchemy
- Docker containerization
- Docker Compose for running multiple services together
- Cloud deployment planning using AWS App Runner and Terraform
- CI/CD basics using GitHub Actions

3. PROJECT FUNCTIONALITY
------------------------

PulseBoard provides these main features:

1. Add a service

The user enters:
- Service name
- Service URL
- Expected HTTP status code

Example:
- Name: Example Website
- URL: https://example.com
- Expected status: 200

The frontend sends this data to the backend using a POST request.
The backend validates the data and stores it in PostgreSQL.

2. View monitored services

The dashboard lists all services stored in the database.
For each service, it shows:
- Service name
- Service URL
- Latest status code
- Latest response time
- Whether the service is online or not

3. Run a health check

When the user clicks "Run check":
- The frontend calls the backend endpoint for that service.
- The backend sends an HTTP GET request to the service URL.
- The backend records:
  - Whether the check passed
  - HTTP status code
  - Response time in milliseconds
  - Any error message
  - Time of the check
- The result is saved in PostgreSQL.
- The frontend refreshes and shows the latest result.

4. View backend API documentation

FastAPI automatically generates Swagger documentation.

Local API docs URL:
http://localhost:8000/docs


4. PROJECT ARCHITECTURE
-----------------------

The project has three main running parts:

1. Frontend container

The frontend is a React TypeScript app.
It runs in an Nginx container after being built.
It is available at:
http://localhost:5173

2. Backend container

The backend is a FastAPI app.
It exposes REST API endpoints.
It is available at:
http://localhost:8000

3. PostgreSQL container

The database stores services and health-check history.
It runs as a Docker container using the official postgres:16-alpine image.

Docker Compose connects all three containers together.

Local flow:

User browser
-> React frontend
-> FastAPI backend
-> PostgreSQL database

Health-check flow:

User clicks Run check
-> Frontend calls backend
-> Backend sends HTTP request to monitored URL
-> Backend stores result in PostgreSQL
-> Frontend displays latest status

7. BACKEND API ENDPOINTS
------------------------

1. GET /health

Purpose:
Checks whether the backend is running.

Response example:
{"status": "ok"}

2. GET /services

Purpose:
Returns all monitored services from PostgreSQL.

Used by:
Frontend dashboard when loading service list.

3. POST /services

Purpose:
Creates a new monitored service.

Request body example:
{
  "name": "Example",
  "url": "https://example.com",
  "expected_status": 200
}

What backend does:
- Validates name, URL, and status code
- Creates a new Service row in PostgreSQL
- Returns the created service

4. POST /services/{service_id}/check

Purpose:
Runs a health check for one service.

Example:
POST /services/1/check

What backend does:
- Finds service with ID 1
- Sends HTTP GET request to the service URL
- Measures response time
- Compares actual status code with expected status code
- Saves result in health_checks table
- Returns the check result

5. GET /services/{service_id}/checks

Purpose:
Returns recent health-check history for one service.

Example:
GET /services/1/checks

19. IMPORTANT INTERVIEW QUESTIONS AND ANSWERS
---------------------------------------------

Question:
What problem does this project solve?

Answer:
It helps monitor whether websites or APIs are online. Users can add URLs, run health checks, and see status code and response time.

Question:
Why did you use PostgreSQL?

Answer:
PostgreSQL is a reliable relational database. It is commonly used in production systems and works well for structured data like services and health-check history.

Question:
Why did you use FastAPI?

Answer:
FastAPI is fast, modern, and easy to use for REST APIs. It also provides automatic validation with Pydantic and automatic Swagger documentation.

Question:
Why did you use React and TypeScript?

Answer:
React is widely used for frontend development, and TypeScript adds type safety, which helps catch bugs during development.

Question:
What is Docker Compose doing?

Answer:
Docker Compose runs multiple containers together: frontend, backend, and PostgreSQL. It also manages networking between them.

Question:
How does the backend connect to PostgreSQL?

Answer:
The backend uses SQLAlchemy with this PostgreSQL connection string:
postgresql+psycopg://pulseboard:pulseboard@db:5432/pulseboard

In Docker Compose, the hostname db refers to the PostgreSQL container.

Question:
What happens when you click Run check?

Answer:
The frontend calls the backend endpoint POST /services/{id}/check. The backend sends an HTTP GET request to the stored URL, measures response time, checks the status code, saves the result in PostgreSQL, and returns the result.

Question:
What is SQLAlchemy?

Answer:
SQLAlchemy is a Python ORM. It lets us define database tables as Python classes and query the database using Python code.

Question:
What is Pydantic used for?

Answer:
Pydantic validates request and response data. For example, it checks that the URL is valid and that the expected status code is between 100 and 599.

Question:
How would you improve this project in the future?

Answer:
I would add authentication, scheduled automatic checks, email or Slack alerts, charts for uptime history, pagination, and production database migrations with Alembic.

26. NEW FEATURES ADDED: EDIT, DELETE, AND HISTORY
-------------------------------------------------

The project now supports more complete CRUD functionality.

CRUD means:
- Create
- Read
- Update
- Delete

In this project:

Create:
You can add a new monitored service from the form.

Read:
You can view all monitored services on the dashboard.

Update:
You can edit an existing service.
Click the edit button on a service row.
The form will fill with the old values.
Change the name, URL, or expected status code.
Click Save changes.
The backend updates the service in PostgreSQL.

Delete:
You can delete a service.
Click the delete button on a service row.
The app asks for confirmation.
If you confirm, the backend deletes the service from PostgreSQL.
Its related health-check history is also deleted because of cascade delete.

History:
You can click History on a service row.
The app shows recent health-check records for that service.
This includes:
- Online or failed result
- HTTP status code
- Response time
- Date and time
- Error message if the check failed

Why these features add value:

Earlier, the project only added and checked services.
Now it behaves more like a real application because users can manage data after creating it.
This makes the project stronger for interviews because you can say you implemented CRUD operations with a PostgreSQL database.

28. HOW TO CHECK IF DATA IS STORED IN POSTGRESQL
------------------------------------------------

This is very important for interviews.
You should be able to prove that data is stored in the database, not just shown on the screen.

Step 1:
Start the project:

cd D:\Project

docker compose up --build

Step 2:
Open the frontend:

http://localhost:5173

Step 3:
Add a service.

Example:

Name:
Example

URL:
https://example.com

Expected status:
200

Step 4:
Click Run check.

Step 5:
Open a second PowerShell window.

Step 6:
Go to the project folder:

cd D:\Project

Step 7:
Open PostgreSQL inside the Docker container:

docker compose exec db psql -U pulseboard -d pulseboard

Step 8:
List all database tables:

\dt

You should see:
- services
- health_checks

Step 9:
Check saved services:

select * from services;

Step 10:
Check saved health checks:

select * from health_checks;

Step 11:
Run a useful join query:

select s.name, s.url, h.ok, h.status_code, h.response_time_ms, h.created_at
from services s
left join health_checks h on h.service_id = s.id
order by h.created_at desc;

Step 12:
Exit PostgreSQL:

\q

Interview explanation:

"To verify persistence, I opened the PostgreSQL container using docker compose exec and queried the services and health_checks tables with psql. This confirmed that the frontend actions were saved in PostgreSQL."
